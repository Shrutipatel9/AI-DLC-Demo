# Post-Review Changes — NFR Requirements, U2 Session Security

This folder keeps the requirement files exactly as the reviewer saw them (review iteration 1, verdict READY; `reviews/review-01.md`). This note amends them. Where they conflict, this note wins, and later stages build to it. All entries are **[Decided by delivery team]**.

| Finding | Change |
|---|---|
| R-01 Lockout scope | During a lockout for a purpose, the following are refused with 429 `CODE_LOCKED` (when visible) or answered silently (when non-revealing):<br>- the verify call for that purpose;<br>- resend for that purpose;<br>- for purpose `login`, also the **password step of `/auth/login`** (the contract lists `CODE_LOCKED` on login, BR1.3).<br><br>**Accepted residual risk:** someone who knows the victim's password can lock the victim's login for 15 minutes, and so can anyone who triggers 5 wrong login codes after a correct password step. The lockout is client-mandated (`AUTH-011`). The per-IP throttle (NFR2.13) slows it. The threat-model row in `security-requirements.md` §5 is superseded by this text. |
| R-02 CORS for cookie endpoints | **New NFR2.17:**<br>- CORS `allow_origins` is exactly the CSRF allow-list (`CSRF_ALLOWED_ORIGINS`, no wildcard).<br>- `allow_credentials` is true.<br>- `allow_headers` include `Authorization`, `Content-Type`, `X-Requested-With`, `X-Refresh-Attempt` and `X-Request-ID`.<br>- `expose_headers` include `Retry-After` and `X-Request-ID`.<br>- Preflight tests for `/auth/refresh`, `/auth/logout` and `/auth/change-password` pass from the allowed origin and fail from any other.<br><br>**Cookie site rule:**<br>- Frontend and API on the same site (for example `app.example.com` and `api.example.com`, or `localhost:3000` and `localhost:8000`) use `SameSite=Lax`.<br>- A cross-site deployment requires `SameSite=None` and `Secure`. The settings validator refuses `SameSite=None` without `Secure`. |
| R-03 Attempt-id handling | Only SHA-256 of the attempt id is stored on the child session. The id must be exactly 22 base64url characters (16 bytes); a malformed id counts as no id, so strict reuse handling applies. The comparison is constant-time. Each rule has a test. |
| R-04 Throttle coverage | NFR2.13 also covers `/auth/refresh` and `/auth/logout`, with a separate, higher per-IP limit (`REFRESH_RATE_LIMIT_PER_MINUTE`, default 60), because many tabs behind one NAT refresh legitimately. |
| R-05 Accessibility of toast and dialog | **New NFR9.9:**<br>- The confirmation dialog moves focus to its first control on open, traps Tab and Shift+Tab, closes on Escape, and returns focus to the opener.<br>- Toasts use `role="status"` (success, polite) or `role="alert"` (error), never take focus, can be dismissed by keyboard, success toasts auto-dismiss after 5 s, and error toasts persist.<br>- Checked by RTL tests and the axe run in Playwright.<br><br>NFR9.1–NFR9.8 are performance targets filed under NFR9 by team decision, as in U1. |
| R-06 Timing test | The anti-enumeration timing test uses at least 200 samples per branch: real account, unknown email, cooldown and locked. Both the median and the p95 differences must stay under 50 ms. It runs under the `perf` marker, so it doesn't slow the coverage run. |
