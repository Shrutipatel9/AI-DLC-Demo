| R-01 | Major | aidlc/spaces/default/intents/260930-client-requirements-buil/inception/domain-design/components.md > component Report > external_dependencies "Headless Chromium" (purpose: "Rendering the PDF from the report page") | The PDF is rendered from "the report page", which is a WebApp screen. That makes Report (backend) depend on WebApp (frontend) at runtime. WebApp depends_on Report, so this is a hidden dependency cycle. It is not declared in depends_on, the diagram or the Rationale. It also conflicts with the team practice that the two apps never depend on each other beyond the HTTP API. The renderer would also need an authenticated session for the private report. | Decide where the PDF layout lives. Either Report renders from a server-side template it owns, or the WebApp-to-Report coupling is declared as a deliberate, documented cycle with an ADR (context, decision, consequences, alternatives rejected) covering auth for the renderer. | New |
| R-02 | Major | components.md > AnalysisRun / Photo / FaceMeasurement.depends_on / ImageGeneration behaviour | FaceMeasurement and ImageGeneration "read the current photos" from MediaStore. Neither depends on PhotoIntake, and AnalysisRun holds no photo-set reference. A retake replaces the Photo and deletes the old file (BR-005, MediaStore "Replacing a file deletes the old one"). So a run that resumes after a restart, or a manual image retry (up to 3 times, later), can read different or deleted photos. The identity check and measurements would then no longer match the photos actually analysed. The design does not say which component owns the run's photo snapshot or how "current" is fixed at start. | Assign ownership of the per-run photo set (for example, AnalysisRun references the file ids captured at start). Declare how FaceMeasurement and ImageGeneration obtain them, and state the rule for retakes after start and for image retry. | New |
| R-03 | Minor | components.md > entities MeasurementSet, ReportText, GeneratedImage, Report (references AnalysisRun owned_by AnalysisPipeline) versus AnalysisPipeline.depends_on | Each of the four analysis components keeps a data reference to AnalysisRun, which AnalysisPipeline owns. AnalysisPipeline in turn depends on each of them (and Report reads their outputs). The call graph is acyclic. The data references point back, so the design has an undocumented reference cycle. The Rationale says "References cross components by id only" but does not call the cycle out, as the stage definition asks for deliberate cycles. | Add a Rationale line stating this is a by-id reference only, with no call dependency and no foreign-key ownership transfer. Alternatively, have the pipeline pass runId as an opaque correlation id. | New |
| R-04 | Minor | components.md > Identity.dependents (Report, ImageGeneration, AnalysisPipeline "Resolves the authenticated user") versus AnalysisPipeline.depends_on Report (async assemble/publish) | The pipeline runs as a background job with no request or user context. It calls Report to assemble and publish, and Report lists Identity and Payments (402) as dependencies for "authenticated user". The design does not say whether background-invoked entry points bypass the auth and entitlement checks or receive a system-trusted user id. This is a security-relevant ambiguity: a 402 or 404 check in a job path should be internal, not HTTP-shaped. | State that the pipeline-invoked operations are internal, take a verified userId and runId, and re-check entitlement, versus the HTTP-facing read paths. Leave the detail to Contract Design. | New |
| R-05 | Minor | components.md > Part A behaviour and external_dependencies; decisions.md ADR-006, ADR-008 | Some implementation choices are fixed at this stage: Web Locks API / BroadcastChannel (ADR-006), shadcn/ui (ADR-008), Headless Chromium (Report), and a PostgreSQL-backed job queue (AnalysisPipeline). The stage definition reserves tech and NFR patterns for later stages. They are recorded with alternatives for the ADR-006 tab-coordination choice, and the rest are stated as consequences. | Mark these as "indicative, confirmed in NFR Design" so later stages are not bound by an inception-level ADR. | New |
| R-06 | Minor | components.md > interaction style values (AnalysisPipeline depends_on FaceMeasurement/ReportWriting/ImageGeneration/Report = async; Report depends_on the same three = sync) | Style is used inconsistently. The pipeline drives its steps as ordered, resumable background steps, and Report reads the same components synchronously. It is unclear whether "async" means a queued job hop or an in-process call within a worker. It matters for the stated retry and resume design. | Add one line defining what async means here (a step executed by the background worker) and that reads by Report and Journey are in-process synchronous queries. | New |

### Summary

The decomposition is sound. Entity ownership is single and the call graph is acyclic. The client's auth layering (UI to Zustand store to API client to Auth APIs to JWT/OTP services) is preserved, and the medical-answer privacy filter and the payment-before-analysis rule are structurally enforced. Two Major gaps deserve the human's attention before approval: the PDF renderer's hidden dependency on the frontend (R-01), and the missing ownership of the per-run photo snapshot (R-02). With two Major and no Critical findings, this stays within the READY threshold.
